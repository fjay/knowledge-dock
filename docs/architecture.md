# 全景架构设计指南

---

## 架构总览与系统拓扑

knowledge-dock 是基于 ActionDock 规范构建的云知识服务与智能体编排工作空间。系统通过 Git 纳管权威事实，以代码变更驱动增量核验，在云端提供权威最新只读视界。

系统端到端总架构拓扑如下：

```text
                 Git Repository (业务代码仓 / 系统知识仓)
                                │
                                ▼
                 Change Detector (检查点基线比对)
                                │
                                ▼
                   Knowledge Maintenance Agent
                                │
               ┌────────────────┴────────────────┐
               ▼                                 ▼
       Knowledge Update                  Knowledge Inbox
     (契约失效驱动更新)                (排障经验缓冲待审池)
               │                                 │
               └────────────────┬────────────────┘
                                │
                                ▼
                  Knowledge Service (HTTPS 443)
           (单端口虚拟视图：查询视图 sk / 维护视图 skm)
                                │
      ─────────────────────────────────────────────────────
      │                         │                         │
  Troubleshooting Agent        IDE / Editor          CLI / Debug Tool
  (线上排障只读检索)        (研发人员日常查阅)        (运维自动化工具)
```

系统由以下核心组件紧密协同构成：

- **代码事实源（Git Repository）**：企业内部托管的代码仓库与系统架构仓库，作为系统唯一的真实事实源；
- **增量检测器（Change Detector）**：负责比对仓库生产分支最新提交与检查点基线水位，筛选出存在有效未审提交的目标仓库；
- **知识维护智能体（Knowledge Maintenance Agent）**：负责分析代码变更影响、执行契约失效评估、提炼候选文档、修复断链并推进基线；
- **知识缓冲区（Knowledge Inbox）**：外部经验与人工补充的受控待审池，阻断未经求证的信息直接写入正式知识库；
- **知识服务中枢（Knowledge Service）**：基于单端口虚拟视图技术，在 HTTPS 443 端口分别提供面向外部的只读查询能力与面向内部的受控维护能力；
- **消费与交互终端**：包含开发者的日常开发工具、排障自动化终端以及线上只读排障助手。

## 核心设计原则在架构中的落地

系统架构严格建立在四大核心工程原则之上：

- **Git 是唯一事实源（Git is Source of Truth）**：架构中不设立独立的外置文档数据库。所有正式知识均以纯文本 Markdown 结构收敛在代码仓专属知识分支中，确保文档与代码同源同宗、具有完整的版本追溯能力；
- **代码变化不等于知识更新（Change does not mean Knowledge Update）**：增量代码提交仅作为触发核验的信号。架构明确将代码重构、单测调整等内部实现与对外契约变更解耦，只有当公开接口、时序契约与业务规则失效时，维护智能体才会执行文件写入；
- **人工贡献统一进入待审池（Human Contribution is Reviewed）**：线上排障经验与人工补充统一进入 Knowledge Inbox 待审池。架构严格限制外部写权限，确保所有人工输入必须经过代码源码交叉比对后方可转正；
- **智能体负责整理维护（Agent modifies knowledge, not humans）**：人类工程师仅需提供关键事实与排障证据，智能体负责承担文档结构对齐、断链校验与分支发布的全部工程开销。

## 知识全生命周期（Knowledge Lifecycle）

在 knowledge-dock 架构中，知识从代码产生到视界分发经历严密的生命周期闭环：

```text
Code Change (研发团队推送业务代码变更)
    │
    ▼
Detect Change (调度器比对提交哈希与检查点基线)
    │
    ▼
Analyze Impact (维护智能体比对源码差异并评估契约影响)
    │
    ▼
Generate Candidate Update (按需生成文档更新或提炼待审候选)
    │
    ▼
Review (零断链门禁校验与业务代码防污染核验)
    │
    ▼
Merge Knowledge (提交推送到专属知识分支 docs)
    │
    ▼
Publish View (更新检查点基线，云端中枢对外分发最新视界)
```

生命周期关键阶段说明：

- **代码变更捕获**：业务代码合并至生产主干分支，产生新的提交记录；
- **增量差异检测**：系统提取最新提交哈希与上一次审计通过的检查点哈希之间的差异代码集；
- **影响范围分析**：维护智能体对差异代码进行语义分析，执行契约失效判定，确认受波及的模块、接口或业务规则；
- **候选文档生成**：若对外契约改变，智能体更新对应目录的知识文档；若是排障经验消费，则将待审池文档提炼合入正式文件；
- **质量门禁审查**：执行零断链门禁检查，确保所有相对链接与锚点完整可用；校验业务代码未受篡改；
- **合并与基线推进**：合入专属知识分支，并将检查点水位推进至当前最新提交，完成增量收敛。

## 运行时物理分层与职责解耦

knowledge-dock 的核心架构设计并非受限于物理位置的本地与远端划分，而是**控制平面与事实平面的职责解耦**，即调度编排与原子能力的彻底分离。

### 控制平面与事实平面职责边界

- **服务端事实平面**（`server/`）：专注于提供纯粹、轻量、无状态的原子能力。承载全局代码镜像、双分支代码同步、差异扫描、检查点基线推进、工作区只读检索与受控编辑以及排障经验待审池。服务端作为全局代码镜像与正式知识体系的权威事实源，对外仅暴露受控动作，不承担任何上层批处理编排调度逻辑；
- **客户端控制平面**（`client/packages/knowledge-orchestrator`）：专注于提供轻量批处理三阶段流水线调度（单仓增量巡检、系统知识跨仓聚合、待审池串行消费）。负责多代码仓按清单巡检、比对增量差异、组装安全命令模板、串行派发智能体任务、轮询探测检查点与候选归档状态并结算审计报告。

### 服务端单端口多视图隔离机制

服务端完全基于 ActionDock 规范构建，统一在标准 HTTPS 443 端口运行，通过鉴权令牌在入口处实现细粒度视图隔离：

```text
               客户端 / 排障智能体 / 开发环境
                             │
       [对外网络暴露面]        │ (HTTPS 443 / 统一单端口)
       ──────────────────────┼───────────────────────
                             ▼
                 ┌───────────────────────┐
                 │    knowledge-server   │
                 │   (ActionDock Serve)  │
                 └───────────┬───────────┘
                             │
             ┌───────────────┴───────────────┐
             ▼                               ▼
       [只读查询视图 sk]              [特权维护视图 skm]
    (ACTIONDOCK_TOKEN 鉴权)       (ACTIONDOCK_AGENT_TOKEN 鉴权)
             │                               │
       ┌─────┴─────┐                   ┌─────┴─────┐
       ▼           ▼                   ▼           ▼
  工作区检索    待审池投递           受控读写    双分支维护
  (只读检索)   (受控追加)           (编辑自愈)  (同步与推进)
```

视图隔离设计特性：

- **只读查询视图**（`sk`）：面向外部日常研发人员与只读排障助手。由只读查询令牌 `ACTIONDOCK_TOKEN` 鉴权，仅开放代码检索、文档读取与受控经验投递，剥离任何文件修改与分支操作能力；
- **特权维护视图**（`skm`）：面向本地流水线调度器与维护智能体。由特权维护令牌 `ACTIONDOCK_AGENT_TOKEN` 鉴权，开放完整的工作区受控编辑、断链自愈、双分支同步与检查点基线推进能力；
- **物理分包单一职责**：服务端底层划分为三个内聚包，分别承载工作区能力（`knowledge-workspace`）、待审池能力（`knowledge-inbox`）与特权维护能力（`knowledge-maintenance`）。

## 仓储双分支治理与免大文件克隆

为了保持工程代码与知识库的整洁共存，系统在仓储管理上执行标准化治理：

- **双分支隔离治理模型**：主干业务分支由研发团队日常提交与发版，保持纯粹的工程业务代码；专属知识分支（`docs`）承载工程知识，文档改动严格收敛在 `docs/knowledge/` 目录下，严禁污染业务代码。合并冲突一律安全中止并由智能体进行语义消解；
- **免大文件部分克隆（Blobless Clone）**：纳管代码仓使用 `--filter=blob:none` 参数克隆，在初始化阶段仅拉取提交元数据与目录树，仅在全文检索或具体读取时按需下载文件内容对象，大幅节约磁盘开销与拉取耗时。
