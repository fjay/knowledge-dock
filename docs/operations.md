## 踩坑经验收件箱：日常投递与整理归纳

在日常研发与排障过程中，工程师常会发现代码中未写明的配置陷阱、网络抖动重试策略或特殊边界限制。若随手修改正式文档，极易造成文档碎片化或格式冲突。系统设立了独立的收件箱待审池，实现安全缓冲与规范沉淀。

### 日常投递踩坑经验

一线研发或运维人员在只读查询配置（`sk`）下，即可直接通过命令行将踩坑经验投递入收件箱待审池：

```bash
ad run knowledge/knowledge.collect --profile sk -- \
  title="支付网关超时重试排障记录" \
  tags.0="payment" tags.1="timeout" \
  content="当支付网关返回网络抖动时，回调接口需校验幂等号并开启指数退避重试，避免重试并发打垮下游服务..."
```

投递的内容将作为独立的候选文件暂存在待审池中，对外不直接暴露检索，完全不影响正常的文档查阅。

### 智能体扫描并整理收件箱

维护智能体在巡检时，负责对待审池中的候选经验进行审核并提炼归并入库：

- 查验待审清单：
  ```bash
  ad run knowledge/knowledge.list --profile skm -- status="pending"
  ```
- 对照源码核实：智能体查阅相关业务源码，核实问题是否属实、当前代码版本是否已自然修复。
- 提炼合并到正式知识库：将经验提炼为标准知识，合并入对应的规范目录中（如将操作步骤合入操作手册目录，将约束合入业务规则目录，将参数合入接口说明目录），绝不机械创建单独的小文件。
- 打标决议并归档：提炼完成后调用归档动作，将记录移出待审池并留痕：
  ```bash
  ad run knowledge/knowledge.archive --profile skm -- \
    id="20260927-a1b2c3d4" \
    resolution="accepted" \
    note="已提炼并合入 order-service 的 runbook-payment.md 操作手册"
  ```

## 检查点打卡机制：为什么没改文档也要打卡？

### 巡检打卡比喻讲透原理

一线维护中最常遇到的疑问是：「我这次提交只是改了内部变量名或补了单测，业务逻辑完全没变，文档不需要改，为什么还要推进检查点打卡？」

答案是：**必须打卡，这是本次巡检完成的法定凭据。**

生活中的打卡比喻：
- 就像保安巡逻整栋大楼，巡查到 3 楼时发现门窗紧闭、一切正常，这时候要不要在打卡器上刷一下巡更卡？
- 当然必须刷卡！刷卡的作用是告诉系统「3 楼我已经认真看过了，确认一切正常安全」。
- 如果不刷卡，系统就会认为 3 楼还没人巡查过。下一轮巡更时，别的保安又得从头跑来把 3 楼仔细查一遍。
- 代码知识库也是完全一样的道理：检查点记录的是「代码已经核验到哪一个提交哈希」。如果因为没有改动文档就不打卡，检查点水位就会停留在上一次的旧位置。下一次调度器定时巡检时，依然会把这部分提交当成新代码，重新拉着智能体查半天，白白浪费算力和时间。
- 当确认无需修改文档时，智能体只需调用完成动作，传入参数 `actionTaken="no_change_needed"` 盖上打卡戳即可：

```bash
ad run maintenance/maintenance.complete --profile skm -- \
  path="/srv/workspace/order-service" \
  commit="a1b2c3d4e5f6..." \
  actionTaken="no_change_needed" \
  summary="内部代码重构与单测补充，未改变任何业务契约"
```

### 失效四问判定法

面对新增代码提交，逐项对照以下四个大白话问题。只要有一个命中，就修改对应文档；四个都不涉及，就直接打卡结束：

- 流程变了吗？主调用链路、分支条件、异步事件发布或异常降级时序变了吗？
- 接口变了吗？对外公开的接口路径、入参、响应字段或错误码变了吗？
- 规则变了吗？业务计算规则、校验阈值、权限门禁或状态流转约束变了吗？
- 数据模型变了吗？数据库表结构、核心实体枚举或持久化字段变了吗？

## 两大红线铁律

### 铁律一：链接绝不能失效（零死链门禁）

在编写或局部编辑 Markdown 文档时，路径拼写错误或章节标题变动极易造成死链，严重破坏知识图谱的连续性。

- 门禁执行时机：在文档修改完成后、正式提交发布前，必须强制执行断链校验动作：
  ```bash
  ad run workspace/links.verify --profile skm -- path="/srv/workspace/order-service"
  ```
- 扫描覆盖范围：自动校验所有 Markdown 文档中的相对路径引用、图片资源以及章节标题锚点。
- 就地自愈修复：若返回断链数量大于 0，必须对照清单就地修改自愈，直到断链数量为 0 时方可进行发布与检查点打卡。

### 铁律二：绝对不能动业务代码（防污染红线）

知识库自维护的核心安全红线是：**任何时候绝不能改动或污染业务源码目录与主干分支！**

- 文档位置收敛：所有知识文档必须严格存放在 `docs/knowledge/` 目录下，严禁在业务源码目录随手创建说明、草稿或批注。
- 分支专属隔离：智能体只能向专属的 `docs` 知识分支推送更新，严禁向 `release`、`main` 或 `master` 等主干分支直接推送修改。
- 提交前状态检查：正式发布前，建议通过命令查看工作区改动状态：
  ```bash
  ad run workspace/bash.exec --profile skm -- command="git status" cwd="/srv/workspace/order-service"
  ```
- 误改紧急回滚：若发现改动列表中混入了任何业务代码文件，必须立即中止发布流程，并执行命令丢弃误改：
  ```bash
  ad run workspace/bash.exec --profile skm -- command="git restore ." cwd="/srv/workspace/order-service"
  ```
