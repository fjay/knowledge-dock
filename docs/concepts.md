# 核心概念与设计原则

---

## 四大核心设计原则

knowledge-dock 的所有架构决策与工程流转均严格遵循以下四项核心设计原则：

### 原则一：Git 作为唯一事实源

- **代码与知识统一托管**：所有正式工程知识均以纯文本 Markdown 格式保存在 Git 仓库中，受完整的版本历史、提交审计与分支权限管控；
- **杜绝外置数据分流**：不引入独立的外部专有文档数据库作为正式事实源，杜绝因外部数据库与代码分支脱节导致的事实漂移。

### 原则二：代码变更只触发检查，知识失效才触发更新

- **变更非更新充分条件**：业务代码发生变更仅代表可能存在知识漂移，是触发审查的必要条件，绝非修改文档的充分条件；
- **契约导向判定**：当一次提交仅包含内部方法重构、私有逻辑抽离或单测扩充时，对外公开接口、核心业务规则与时序契约并未改变，既有文档依然准确有效，此时严禁更新文档；
- **增量收敛铁律**：无论文档是否需要修改，维护流程结束后均须坚决推进检查点基线，确保下一次巡检不发生冗余重复比对。

### 原则三：人工贡献统一进入待审池统一评审

- **待审池物理缓冲**：线上故障处置中提炼的排障经验与日常人工补充，一律先写入 Knowledge Inbox 待审池，严禁直接推送正式知识分支；
- **源码交叉求证**：待审池文档必须由维护智能体结合当前代码仓源码进行交叉比对核验，确认属实后方可提炼转正；
- **阻断主观污染**：待审池机制构筑了一道不可逾越的防火墙，有效过滤未经验证的主观臆测与偶发孤证。

### 原则四：人提供事实，智能体负责整理

- **人机协同分工**：人类研发人员擅长洞察异常现场、捕获日志证据与验证排障结果，但在高频迭代下极难保持文档格式规范与全局一致性；
- **智能体承接工程开销**：智能体负责承担文档结构切片、超链接有效性核验、跨文档影响评估以及分支提交等繁重的工程性维护开销，实现人机协同效率最大化。

## 核心系统概念与术语规范

### 单端口虚拟视图权限隔离

在标准 HTTPS 443 单一端口下，基于 ActionDock 原生虚拟视图特性，仅通过请求头中的鉴权令牌实现视图与能力隔离，无需前置反向代理网关：

- **只读查询视图**（`sk`）：面向外部研发人员与只读排障助手，由只读查询令牌 `ACTIONDOCK_TOKEN` 鉴权，仅暴露工作区全文检索、受控文件直读以及 Knowledge Inbox 候选经验投递能力；
- **特权维护视图**（`skm`）：面向本地流水线调度器与维护智能体，由特权维护令牌 `ACTIONDOCK_AGENT_TOKEN` 鉴权，开放完整的工作区受控读写、双分支同步、增量扫描与检查点基线推进能力。

### 事实平面与控制平面职责解耦

系统在架构上明确划分为服务端事实平面与客户端控制平面：

- **服务端事实平面**（`server/`）：专注于提供纯粹、轻量、无状态的原子能力。承载全局代码镜像与正式知识库，对外仅暴露受控 Action 动作，不承担任何上层批处理编排逻辑；
- **客户端控制平面**（`client/packages/knowledge-orchestrator`）：专注于提供轻量批处理三阶段流水线调度。在当前执行机环境中运行，命令行严禁附加全局控制选项，负责巡检多仓、组装模板、派发智能体任务并结算审计报告。

### 双分支隔离治理模型

在底层纳管的代码仓库中，系统实行严格的双分支管理策略：

- **主干业务分支**：如 `release` 或 `main` 分支，由人类业务开发团队日常提交与发版，保持纯粹的工程业务代码；
- **专属知识分支**：统一命名为 `docs` 分支，承载该代码仓的工程知识文档。文档改动严格收敛在 `docs/knowledge/` 目录下；
- **冲突安全中止**：同步分支时若检测到代码级冲突，自动化程序严禁私自裁决，立即安全中止（`git merge --abort`）并退出，交由智能体进行语义消解。

### 检查点基线推进机制

系统为每个纳管仓库维护检查点基线水位记录（`last_knowledge_checked_commit`）：

- **增量扫描基准**：每次巡检时，系统比对业务分支最新提交哈希与已记录的检查点哈希，仅将存在有效新提交的仓库标记为待处理任务；
- **推进基线的技术必要性**：推进水位是系统标记「该段代码差异已经通过完整知识维护流程核验」的唯一凭证。无论代码变更是否触发文档改动，推进基线均为标记该批次提交已通过完整审计与评估的凭据；若不推进检查点，后续维护将持续对已审计代码重复发起冗余比对与全量扫描，破坏增量闭环收敛性并带来不必要的计算开销。

### 排障经验待审池

Knowledge Inbox 是所有人工知识进入正式知识库前的审核缓冲区：

- **结构化候选格式**：采用标准 Markdown 格式，由 YAML Frontmatter 与语义标记节构成；
- **候选文档解耦定位**：候选文档是贡献单元，不是正式知识存储单元。维护智能体将其作为提炼原料，核验属实后合入既有知识骨架目录，随后执行归档移出，保证待审池流转收敛。

### 质量门禁与防污染红线

在正式提交发布知识更新前，系统强制执行两道质量红线：

- **零断链门禁**：通过 `links.verify` 校验动作，对所有内部引用、相对路径与锚点进行完整性扫描。发现失效引用立即就地自愈修复，断链数量归零后方可放行；
- **业务代码防污染红线**：文档生成与更新严格收敛在 `docs/knowledge/` 目录下，严禁在业务源码目录生成临时文件或修改业务代码。提交前通过差异核验，一旦检测到业务文件改动立即全部回滚并阻断发布。
