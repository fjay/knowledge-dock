# 核心概念与设计原则

> 工程知识治理的核心不是制定严苛的人工撰写规章与考核指标，而是构建不随智能体状态波动与执行偏差而失效的系统不变量体系。

---

## 系统核心不变量体系

[`knowledge-dock`](file:///root/code/knowledge-dock) 的所有架构决策与运行流转均建立在五条硬性系统不变量之上，以此抵御环境漂移与概率性智能体的认知缺陷：

### 单一事实源不变量

- **代码与知识版本同构**：所有正式工程知识均以纯文本 Markdown 结构保存在 Git 仓库的专属知识分支中，受提交历史、差异比对与分支安全策略约束；
- **杜绝外置独立数据库孤岛**：不引入独立的外部知识数据库作为正式事实源，消除多数据源之间的版本时差与同步断裂。
- **缺失机制的系统灾难**：若脱离 Git 仓库引入外部专有文档数据库，业务代码分支与文档版本将失去原子绑定关系。在微服务多分支并发开发或紧急线上回滚时，外部数据库无法识别对应的代码基准，导致查询出的时序契约与生产实际执行的代码完全相左，形成无法自证事实的孤岛数据。

脱离 Git 提交历史的代码解释，等同于无法被编译验证的无效代码。

### 双分支隔离不变量

- **双分支解耦治理**：统一规范表述为「双分支隔离治理模型」，主干业务分支与知识分支解耦，遇冲突安全中止并由智能体进行语义消解；
- **业务主干分支纯粹性**：如 `main` 或 `release` 分支，由业务研发团队日常提交与发版，仅包含纯粹的工程业务代码；
- **专属知识分支独立性**：统一命名为 `docs` 分支，承载工程知识文档，文档变更严格收敛在 [`docs/knowledge/`](file:///root/code/knowledge-dock/docs/knowledge/) 目录下；
- **冲突安全中止机制**：分支合并时若检测到代码级冲突，自动化程序严禁私自裁决，必须立即安全中止并退出，交由具备上下文感知能力的智能体进行语义消解。

```bash
# 双分支增量同步状态机逻辑
git checkout docs && git merge --no-ff origin/main
if [ $? -ne 0 ]; then git merge --abort; exit 1; fi # 发生代码级冲突立即安全中止，交由智能体语义消解
```

- **缺失机制的系统灾难**：若将知识文档与业务源码混在单分支提交，高频的文档补丁会严重污染业务提交日志，甚至意外触发持续集成发版流水线；更严重的是，若自动化脚本在遇到代码冲突时擅自执行强制覆盖或硬重置，将导致真实的业务功能代码被静默抹除，直接酿成严重生产故障。

业务分支的纯粹性是生产安全的底线，知识分支的独立性是演进治理的前提。

### 检查点推进不变量

- **增量扫描基准锚定**：统一规范表述为「检查点基线推进机制」（基于提交哈希的增量扫描基准）；
- **推进基线的技术因果必然性**：无文档变更时推进检查点的技术必要性在于：无论代码变更是否触发文档改动，推进基线均为标记该批次提交已通过完整审计与评估的唯一凭据；若不推进检查点，后续维护将持续对已审计代码重复发起冗余比对与全量扫描，破坏增量闭环收敛性并带来不必要的计算开销；
- **缺失机制的系统灾难**：在企业工程实践中，大量的代码提交属于内部重构、性能微调或单测扩充，其业务契约与对外接口并未改变，无须修改文档。此时若系统因没有文档改动而不推进检查点水位，下一次巡检依然会将这些已审提交判定为未审计差异，导致系统每一次巡检都陷入全量扫描与比对的死循环，最终耗尽计算资源并阻塞后续真正需要处理的新提交。

没有更新内容的检查点推进，恰恰是对系统代码稳定、知识无须介入的最高确认。

### 待审池缓冲不变量

- **缓冲入池物理隔离**：统一规范表述为「排障经验待审池」，规范候选经验结构化采集、特权审查提炼与决议归档留痕闭环；
- **贡献单元与存储单元解耦**：候选文档是贡献单元而非正式知识存储单元，严禁机械地一对一新建正式文档；
- **源码交叉求证机制**：排障经验待审池中的候选文档必须由维护智能体结合目标仓库源码事实进行深度交叉比对，确认具有普适性而非环境孤证后，提炼并合入既有知识骨架目录，随后执行归档移出，保证待审池流转收敛；
- **缺失机制的系统灾难**：排障现场往往伴随主观猜测与偶发特例。若不设待审池物理缓冲而允许直接修改知识库，未经验证的碎片化记录将迅速稀释正式知识体系的密度，使知识库退化为充满矛盾信息的排障废纸篓。

未经源码交叉求证的排障经验不仅不是知识，反而是误导后续诊断的潜在系统缺陷。

### 发布质量不变量

- **零断链质量门禁**：统一规范表述为「零断链门禁」（`links.verify` 就地自愈），对所有 Markdown 相对引用与内部锚点执行完整性核验，断链数归零前阻断发布；
- **业务代码防污染红线**：统一规范表述为「业务代码防污染红线」（严格收敛在 [`docs/knowledge/`](file:///root/code/knowledge-dock/docs/knowledge/) 目录），提交前严格核对暂存区变动，一旦检测到文档目录之外的代码文件改动，立即触发全量回滚并中断发布；
- **缺失机制的系统灾难**：断链会导致智能体或工程师在紧急排障沿着参考路径跳转时遭遇死胡同，造成排障上下文断裂；而若缺乏防污染红线拦截，概率性智能体在编辑或排查过程中产生的临时脚本、测试用例或误改代码一旦合入仓库，将直接污染代码仓库甚至引发非预期的业务缺陷。

自愈不是辅助功能，而是阻止知识孤岛产生与保证闭环交付的必备安全阀。

## 单端口虚拟视图权限隔离

统一规范表述为「单端口虚拟视图权限隔离」（Virtual Views），基于只读查询令牌 `ACTIONDOCK_TOKEN` 与特权维护令牌 `ACTIONDOCK_AGENT_TOKEN` 在 443 端口实现细粒度动作暴露隔离。

系统在标准 HTTPS 443 单一端口下，利用 ActionDock 原生虚拟视图能力依据请求头中的鉴权令牌自动划分暴露面，彻底省去前置反向代理网关与复杂的端口映射：

| 视图类型 | 鉴权凭据与角色 | 动作暴露面与安全约束 |
|---|---|---|
| 只读查询视图（`sk`） | 只读查询令牌 `ACTIONDOCK_TOKEN`<br/>外部开发者、只读排障助手 | 暴露工作区全文检索、受控文件直读、目录浏览与排障经验待审池受控追加，协议层物理剥离写入与 Git 维护能力 |
| 特权维护视图（`skm`） | 特权维护令牌 `ACTIONDOCK_AGENT_TOKEN`<br/>受信任维护智能体、本地调度器 | 开放工作区受控写入、精准编辑、双分支增量同步、零断链门禁校验、发布提交与检查点基线推进完整能力 |

若不进行单端口虚拟视图权限隔离，混淆只读与特权边界，外部只读查询请求便有可能误触发破坏性写入操作；而若采用多端口或多容器方案进行权限物理隔离，则会大幅增加网络攻击暴露面与容器编排的维护成本。

最严密的安全防线不是增设代理网关层级，而是在单个接入端口上依据凭据对动作暴露面的物理熔断。

## 双平面职责解耦架构

统一规范表述为「客户端控制平面」（纯本地控制动作，命令行严禁附加 `--profile` 控制选项）。系统在逻辑架构与运行时边界上划分为两个正交平面：

| 平面分层 | 运行主体与约束 | 核心职责与边界 |
|---|---|---|
| 服务端事实平面 | 独立容器运行环境<br/>收敛于 443 单端口 | 承载代码镜像、双分支治理、检查点水位与待审池，对外仅提供纯粹、轻量、无状态的受控原子动作，不承担批处理编排逻辑 |
| 客户端控制平面 | 当前执行机纯本地运行<br/>命令行严禁附加 `--profile` 控制选项 | 流水线调度器（[`knowledge-orchestrator`](file:///root/code/knowledge-dock/client/packages/knowledge-orchestrator)）纯本地驱动三阶段调度，负责仓储巡检探测、安全模板渲染、智能体派发与审计报告结算 |

事实平面专注提供原子能力，控制平面专注决定执行时序，职责彻底分离杜绝状态污染。

---

## 结语：架构全貌收敛法则

整个系统全貌遵循四句话收敛法则：

- 五条系统不变量构筑了工程知识生命周期的底层物理规律。
- 单端口虚拟视图在网络边界以最小暴露面捍卫事实纯洁性。
- 事实平面与控制平面彻底解耦，保障分布式环境下的无状态轻量化交互。
- 确定性的工程防御机制终结了概率性幻觉，赋予云端知识中枢持续可信的生命力。
