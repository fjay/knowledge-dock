# 以端到端流程发现知识

目标是尽量不遗漏重要行为、分支与约束，同时让已发现但未深入的主题可查找。发现与调查分开；不把文件分类、已写篇数或计划完成率当作业务覆盖。

## 先广度发现

围绕本次范围，查看入口装配、注册表、公共导出、已有文档和测试组织。按实际适用情况寻找：

- HTTP/RPC/CLI/工具调用和用户操作入口；
- 消息消费者、事件监听、回调、定时任务和后台作业；
- 启动、关闭、恢复、导入、清理与迁移等生命周期行为；
- 状态写入、任务投递、外部调用及故障处理测试暴露的行为。

目录名用于缩小搜索范围，入口数量也不直接等于流程数量。通用库的公共调用能力同样可能是流程入口，不只寻找 Web Controller。

广度发现的入口清单直接决定各类别文档的选题。发现不限于主 Agent 亲自执行：项目较大时按模块或入口类型拆给多个子代理并行发现，主 Agent 汇总候选清单后规划选题。初始化与重建按六个类别目录（flow、module、rule、interface、data、runbook）组织产出，布局与命名按 layout.md 执行，每个类别至少一篇实质文档；确无对象的类别按 layout.md 的省略规则在索引与报告中显式声明，不得静默跳过。

在知识索引保留紧凑流程表：行为/问题、真实入口线索、文档或小节、已发现/已调查/缺口/不适用及原因。候选也要出现，但不链接尚不存在的文件。边探索边修正，不要求 Agent 在读代码前就给出完整计划。

## 再沿行为深入

优先调查核心业务、状态变化和重要失败路径，先交付一篇有用的完整流程，再扩展其它主题。广度阶段发现的其它流程保留可见。

每条流程追到业务结果或明确外部边界：

`触发 → 校验 → 关键调用/状态变化 → 同步或异步交接 → 后续处理 → 可观察结果`

沿途检查：

- 调用/投递由谁发起，谁处理，实际输入输出是什么。
- 队列、事件、回调如何衔接；靠什么业务 ID、任务 ID 或关联键识别同一次流程。
- 谁拥有状态、谁推进下一步，持久化与外部副作用按什么顺序发生。
- 校验失败、下游失败、超时、取消、重试与重复执行如何处理；已发生的副作用如何收尾。
- 关键节点对应哪些实现、调用方和测试。未运行测试只说明其预期，不声称运行验证。

跨文件、模块、进程或仓库不应让流程解释中断。跨仓追踪按 cross-repository.md 核对双方证据；只有一侧代码时明确停在哪个边界。

## 合理拆分

独立业务目标、独立触发与结果、独立状态生命周期或失败恢复策略，可以构成独立流程。共享同一实现的多个入口可以合写，并分别记录入口差异。

长流程页保留端到端路径、关键分支和交接，复杂片段链接子流程；公共权限、幂等或配置规则写专题供多个流程引用。拆分后不能只剩“调用另一服务”，必须说明交接契约和继续查找的位置。

允许同一个文件参与多个流程。不要为每个目录/函数建一篇文档，也不要把多个独立行为压成 overview 的一句话。

## 最后反向补漏

从实际代码重新核对，而不只重读文档地图：

- 注册表/装配代码中的入口，是否都有流程归属或明确处置？
- 发出的事件/任务，接收方及后续结果是否已找到？消费者的上游是否清楚？
- 关键状态由谁写入、谁继续推进，终态和失败状态是否解释？
- 测试、错误码、日志和配置揭示了哪些未记录分支、恢复路径或行为开关？
- 流程之间是否缺了调用、关联键或状态交接？
- 六个类别目录是否都已建齐且各含至少一篇实质文档？省略的类别是否已在索引声明依据？

不要求每个分支独立成篇，但重要分支必须能从流程找到。文件属于 supporting、test、config 不消除其中的行为线索。无证据时保留缺口，不批量填“不适用”。

## 三类信息保持独立

- 已发现：知道行为存在及其入口，但可能尚未深入。
- 已调查：正文解释了本次范围内的重要行为和定位。
- 缺口：哪条链路或哪个约束还不清楚，下一步应查哪里。

未知的流程无法靠清单保证穷尽；如实说明本次扫描边界和未调查部分。用户只要求局部主题时，完成局部范围并记录相关发现，不自动扩大全仓工作。
