# 仓库层与系统层

同一套 Markdown、流程模板和元数据用于两层知识。仓库层记录本仓实现与对外交接点；系统层连接跨仓端到端流程，解释服务责任、交接、关联标识、状态归属和故障传播。

## 位置与仓库映射

单仓默认写本仓 `docs/knowledge/`。系统层写用户指定的知识目录、文档仓库或已授权工作区。系统层目录按 [layout.md](layout.md) 的系统层布局组织：根目录一个系统 `index.md`（领域清单 + 仓库映射），每个业务领域一个目录，领域内部与仓库层完全同构；新建领域一次建齐全部类别目录。先利用当前会话已给出的路径判断；若多个位置都合理且目标未知，再询问一个输出位置，期间可以继续只读调查。

### 业务领域识别与仓库归属三步法

在多仓库微服务体系下，系统知识库按业务领域组织跨仓知识。智能体遵循极简自愈原则，无需依赖外部扫描器，按以下三步法完成业务领域识别与仓库归属：

- **第一步（权威基线）**：优先采信用户提供的全仓职责索引文档（若存在）；
- **第二步（常识预判、仓内印证与自动化依据链提取）**：未提供索引或面对新增未登记仓库时，智能体基于仓库命名与业务定位形成语义常识预判（如订单履约、跨境结算、用户中心等），随后主动调阅各代码仓已有的 `docs/knowledge/overview.md` 系统概览与 `index.md` 导航，核查核心系统目的与职责边界。同时，必须基于兄弟代码仓中的代码客观事实提取自动化证据链，杜绝凭空推测：
  - 源码接口与路由契约：扫描 Controller、RPC 接口与路由定义，明确对外暴露的业务能力；
  - 消息队列事件：扫描 MQ 主题生产者与消费者、消息载荷结构及队列绑定，厘清异步事件归属；
  - 数据库资产与变更：调阅 Flyway 迁移脚本、DDL 变更与持久化实体模型，核对关联库表与状态流转；
- **第三步（全景探索、自主决策与跨仓聚合）**：系统知识库维护必须全流程全自动自主推进，严禁终端挂起等待人工干预：
  - 全景主动探索与自主决策：严禁仅凭增量提交未触碰业务源码（例如仅改动依赖配置）便偷懒判定免更，必须主动横向排查工作区所有代码仓，核实未纳管仓库、存量六大分类目录完整度与跨仓链路完备性。智能体基于代码客观事实自主推导判定与规划演进，直接受控委派写入，严禁在终端输出任何等待确认的阻塞交互；
  - 系统层固化与跨仓聚合：自主推导完成后，在系统知识库根目录 `index.md` 中维护「业务领域清单 + 代码仓归属对照表」，并在对应的领域目录（如 订单履约/、跨境结算/）下聚合端到端跨仓流程文档（`flow/`）并汇总数据库映射至根目录 `db-map.md`。若为全新业务领域，必须一次建齐全部六大分类单数目录。

在容器运行环境中，所有纳管代码仓与系统知识仓均统一部署在统一工作区根目录 `/srv/workspace` 下，呈现同级平铺的拓扑结构（例如 `/srv/workspace/<target-repo>` 与 `/srv/workspace/system-knowledge`）。ActionDock 所有工作区动作均使用绝对路径。智能体在单一代码仓内执行维护任务时，完全被授权且应当主动以绝对路径直接访问兄弟代码仓（`/srv/workspace/<sibling-repo>`）与系统知识仓（`/srv/workspace/system-knowledge`），核验源码实现、接口契约以及全局资产，消除视野盲区，杜绝凭空推测。

生产库 DDL 统一存系统层：根目录 `db-map.md` 登记库名、领域与域名的映射，结构快照统一存根目录 `ddl/data-ddl-{schema}.md`（含「字段语义补丁」节，重导自动保留）；仓库层仅以 `data/data-databases.md` 引用，不持有结构文档。细则见 [layout.md](layout.md)。

系统层索引维护仓库表：稳定标识、职责、源码获取位置/已知托管地址、仓库知识入口、可访问性和版本边界。单仓也保留自己的标识。需要时从 Git remote 读取规范仓库身份，但不要记录带凭据的 URL。

可共享文档不硬编码个人机器绝对路径。实际 checkout 路径使用用户提供的环境或会话映射；相对布局可在当前工作区索引说明。不要编造仓库 URL，不因登记仓库就隐式克隆或修改所有仓库。

## 事实归属

局部实现只有一个主要说明位置。例如消费者去重逻辑归所属仓库流程/规则；系统页链接它并说明对端到端行为的作用，避免复制一整份实现描述。

系统页自身需要说明的事实包括：为什么这些片段构成同一业务链路、消息与请求如何交接、业务标识如何对应、谁拥有状态、跨服务失败如何传播。跨仓流程需要推理与核实，不能仅把局部 Markdown 拼接起来。

无需等待所有仓库建库完成才写系统流程。可直接核查双方源码、引用已存在的局部文档；尚无局部文档时给真实代码定位，不创建悬空文档链接。只在本次授权范围内写入。

## 确认交接

每个重要跨仓连接核对：

| 项目 | 证据 |
|---|---|
| 生产与消费位置 | 两侧注册、调用/发送、处理实现 |
| 传输契约 | 方法/路径、主题/队列、消息结构、版本与配置绑定 |
| 业务关联 | 订单 ID、任务 ID、关联键、状态字段及两侧实际用法 |
| 错误与重复 | 确认/重投递、超时、幂等、重试/补偿及各方责任 |
| 运行边界 | 已调查的代码版本，以及部署组合是否另有依据 |

同名事件不等于已建立连接。topic 默认值、环境覆盖或服务版本不同，都可能改变实际关系。源码只能证明代码支持的关系；未核对运行环境时不宣称线上必然如此。

一侧不可访问时，描述可见调用端和已知契约，把另一侧及后续结果标为未验证。不要凭常见架构补全消费者行为。系统覆盖仅针对已声明范围，仓库缺失不掩盖为“已完成”。

## 面向 Agent 的查询与变更

Agent 先按业务问题或接口、事件、日志、错误码在索引定位，再进入系统流程、局部片段与源码。排障沿失败节点和关联键定位；设计沿契约、状态归属和上下游影响定位。

源码变化先核对本仓知识。只有局部变更影响对外契约、关键状态、交接或失败行为时，才检查引用它的系统流程和上下游约束；内部重构可能仅需更新定位。没有受影响仓库的权限或源码时，记录明确待核对项，不捏造已完成跨仓验证。

## 系统知识库提交与推送

当单仓变更联动修改了系统知识库（`system-knowledge`）中的领域流程、DDL 快照或映射表时，修改必须及时闭环推送到远端：

- **直接推送权限**：系统知识库允许维护智能体自动维护并直接推送到 `origin/master` 分支，无需挂起或提审。
- **提交动作**：调用 `maintenance.publish` 动作完成闭环提交与推送：
  ```bash
  ad run maintenance.publish --profile skm -- path="/srv/workspace/system-knowledge" repoType="system_knowledge" message="docs(system): sync payment domain flow from order-service"
  ```
- **避免脏工作区**：未提交的本地修改会导致后续定时同步或他人同步时触发 `dirty_worktree` 阻断，因此跨仓修改后必须当场或在流水线收尾时统一执行 `maintenance.publish`。
