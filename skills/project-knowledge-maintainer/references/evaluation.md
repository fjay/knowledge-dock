# 技能维护者验证

正常建库无需读取。本技能首先交付指引、模板和元数据约定；静态校验只能检查包结构和引用，不证明真实建库效果。

## 包检查

检查 SKILL.md frontmatter、模板与 metadata.md 的字段一致性、按需阅读链接、单仓/跨仓定位约定，以及三个使用场景是否有相应内容要求。核对 layout.md 的骨架与 SKILL.md 内联骨架、模板 kind、metadata id 公式互相一致。模板空值属于待填写骨架，不得作为已完成的项目文档交付。

包不应携带运行时脚本、哈希账本、固定角色链、阶段 JSON 或旧版迁移流程。Git 提交只作为可选核对线索，不能变相要求手填文件指纹。

## 行为案例

后续用真实 Agent 试运行时，分别检查：

- 多入口单仓建库：发现独立业务、异步消费者和失败路径，索引保留已发现与已调查差异，不以一篇 overview 完工。
- 跨仓流程：核对两侧契约、关联键和状态责任；同名事件不能直接认定连接，缺失仓库不能编造行为。
- 排障：用真实错误码或现象找到流程节点及可区分原因的检查，最后定位代码。
- 设计：从拟修改能力找到现有约束、调用方/消费者和测试；建议不混入当前事实。
- 业务理解：从角色或操作找到完整路径，跨篇拆分后交接仍然明确。
- 局部维护：只更新受影响事实和导航；新增未引用入口也应被发现，不要求全仓重写。
- 未提交代码变化：工作区差异和未忽略新文件纳入调查，不用 HEAD 冒充准确内容版本。
- 只读审查：报告错误和缺口，不修改文档或推进 checked_commits。
- 类别完整与命名统一：初始化后六个类别目录齐全、每类至少一篇实质文档；文件名符合 `{kind}-{topic}.md`；多生产库 DDL 每库一篇 `data-ddl-{schema}.md`，`db-map.md` 登记库名、领域与域名映射，仓库层仅 `data-databases.md` 引用；省略的类别在索引与报告中有显式依据。跨多个项目与系统层领域对比，目录与命名应完全一致，不随项目或领域变化。
- 大仓委派编排：主 Agent 只做决策与验收，广度发现、各类别文档、index/overview 起草均可由子代理完成；委派不因项目小而跳过类别，交接靠文件位置与摘要，无同文件冲突编辑。
- 更新门槛：行为无关的小改动（私有重构、格式化、测试调整、未记载配置的默认值变化）正确判定为不更新，且在回复用户的完成报告中留痕（不写入文件）；定位改名与契约变化不因“改动小”被跳过；拿不准时更新且范围限于失效条目，不顺带重写。

## 对比方法

固定仓库版本、模型、宿主工具、任务范围和预算，在独立工作区比较普通 Markdown 工作流、旧技能和本技能。跨仓案例固定各仓版本及可访问范围。

在建库前准备有代码依据的问题，涵盖流程理解、错误定位、设计约束及异步关联。评估者先使用知识再回查源码，不提前提供建库者预期答案。

记录逐题正确性、证据支持、遗漏、能否定位实现、需要重新探索的工作量，以及首篇可用文档时间、总耗时、调用量和重试。文档篇数、字数和角色完成数量不作为主要指标。

未实际运行时只提供评估案例，不能填写模拟分数或宣称真实 Agent 效果已提升。单次小仓试验也不能证明全仓或跨仓普遍可靠。
