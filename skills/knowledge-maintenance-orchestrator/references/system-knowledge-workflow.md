# 参考手册：系统知识库多子代理协同规程

本文档作为系统知识库全局聚合维护的微观执行规程，规范主智能体统筹专业子代理，基于工作区兄弟代码仓提取客观事实证据，执行全景探索、自主决策、受控写入与验收推进的三阶段全自动自闭环。

---

## 系统知识库协同核心铁律

主智能体统筹系统知识库维护任务时，坚决贯彻轻量与极简原则，各角色纯粹通过清晰的职责陈述进行自然分工，严格执行以下铁律：

- 主智能体统筹不盲动：主智能体作为系统层知识维护总控中枢，负责全局统筹、自主规划、子代理调度委派与最终门禁验收，绝不亲自盲目编辑文件。
- 全流程全自动自闭环铁律：流水线全流程自动化无人值守运行，严禁在终端向用户提问、索求确认或挂起等待，严禁输出任何交互确认话术，所有推导与规划均为内部自主决策推进。
- 全景主动探索防偷懒铁律：系统知识库承担全局资产治理职责，严禁仅凭增量代码未触碰业务源码（例如仅改动依赖配置）便草率判定免更；必须主动横向排查工作区所有代码仓，核实未纳管仓库、存量六大分类目录完整度与跨仓链路完备性。
- 自动化证据驱动杜绝臆测：业务领域归属与跨仓影响必须基于兄弟代码仓中的对外暴露接口、消息队列事件与数据库变更等客观代码事实推导判定，严禁凭空臆测。
- 零断链验收与推进检查点：修改完成后必须调用 `workspace/links.verify` 校验并达成零断链；最后必须调用 `maintenance.complete` 推进检查点水位，完成闭环交付。

## 角色定位与协同分工矩阵

系统知识库维护涉及跨多仓全局视角，采用主智能体统筹与专业子代理分工协同架构，主智能体负责统筹与把关，各专项子代理各司其职：

| 协同角色 | 职责定位 | 核心工作内容 |
|---|---|---|
| 主智能体 | 总控统筹与门禁中枢 | 负责全局统筹、证据调查委派、自主方案制定、写入任务分派、零断链验收与检查点推进 |
| 跨仓契约与领域影响分析子代理 | 事实提取与决策推导 | 横向扫描工作区兄弟仓提取接口、事件与数据库客观证据，研判跨仓影响，执行三路决策树推导 |
| 新领域初始化子代理 | 骨架搭建与索引登记 | 负责开辟全新业务领域目录骨架、一次建齐全部六大分类目录及基础导航，并在系统总索引登记 |
| 跨仓主流程子代理 | 业务编排与流程起草 | 负责梳理跨服务端到端协作流程、时序、关联键流转与失败补偿，起草或更新主流程文档 |
| 接口与数据模型子代理 | 契约核验与模型映射 | 负责核对跨服务接口契约、消息事件，维护全局数据库映射表与结构快照 |

## 第一阶段：全景事实探索与自主推导决策

主智能体统筹调度专业子代理对工作区开展全景纵深探索与事实核验，杜绝仅凭增量文件后缀草率判定，全流程自主决策推进：

- 全景资产反查与主动探索门禁（防偷懒铁律）：
  - 严禁仅凭增量提交未触碰业务源码（例如仅升级依赖或修改构建配置）便草率判定无需更新。
  - 必须横向扫描工作区平铺的全部代码仓（`/srv/workspace/*`），对照系统总索引 `index.md` 检查是否存在未纳管的物理代码仓。
  - 调阅各代码仓前序巡检生成的单仓文档，检查是否存在未沉淀至系统层的跨仓主流程或接口契约。
  - 检查存量业务领域是否缺失六大分类目录或导航文件。
  - 检查全局数据库映射 `db-map.md` 与 DDL 快照 `ddl/` 是否完备。
- 自动化证据链提取技术路径：
  - 源码接口与路由：使用 `workspace/search.rg` 检索 Controller、路由定义、RPC 契约与对外暴露服务。
  - 消息事件与流转：使用 `workspace/search.rg` 检索消息队列主题生产者与消费者、消息载荷与队列绑定，梳理异步事件流动。
  - 数据库资产与变更：使用 `workspace/files.read` 与 `workspace/search.rg` 调阅 Flyway 迁移脚本、DDL 变更与持久化实体，确认库表结构与数据源映射。
- 三路自主决策树判定：
  - 路径一（开辟新业务领域）：发现未纳管独立代码仓或全新业务线契约时，执行业务领域识别与目录初始化三步法（调阅根目录 `index.md` 清单、扫描工作区未纳管代码仓、研判业务归属），判定为开辟新业务领域（`create_new_domain`），自主规划领域命名、目录骨架与映射关系。
  - 路径二（更新已有领域）：核验跨仓影响是否破坏存量有效性，或存量业务领域存在知识缺漏，若触及行为层主流程变化、契约层接口或消息事件变动、数据层表结构或持久化实体调整、或存量六大分类目录缺漏，判定为更新已有领域（`update_existing_domain`），提取具体影响点并规划更新方案。
  - 路径三（无需更新 - 高门槛严格兜底）：仅在完成上述全景主动探索、确证所有物理仓均已登记纳管、存量业务领域六大分类目录完整健全、跨仓端到端主流程与全局数据库资产无任何缺漏，且前序提交经核验确未破坏对外契约与跨仓流程时，方可审慎判定为无需更新（`no_change_needed`）。
- 自主方案规划（不挂起终端）：
  - 主智能体自主生成演进决策记录，明确影响范围与委派分工，直接转入第二阶段受控写入。
  - 演进方案内部记录格式：

```markdown
# 业务域演进方案记录

- 判定结论：<开辟新业务领域 / 更新已有业务领域 / 无需更新>
- 目标领域：<业务领域中文名，如 订单履约>
- 客观推导证据链：
  - 接口契约变动：<代码仓名及文件路径 file:///srv/workspace/...，接口变更摘要>
  - 消息事件变动：<代码仓名及文件路径 file:///srv/workspace/...，MQ 主题及载荷变更>
  - 数据库资产变动：<代码仓名及文件路径 file:///srv/workspace/...，DDL 脚本或表结构变动>
- 拟变更系统知识库资产清单：
  - 涉及目录：file:///srv/workspace/system-knowledge/<业务领域中文名>/
  - 拟新建或更新文件：
    - file:///srv/workspace/system-knowledge/<业务领域中文名>/flow/<category>-<topic>.md（主流程说明）
    - file:///srv/workspace/system-knowledge/<业务领域中文名>/interface/<category>-<topic>.md（契约说明）
    - file:///srv/workspace/system-knowledge/db-map.md（全局映射更新）
- 专业子代理委派计划：
  - <委派角色与职责简述>
```

- 全自动推进规程：
  - 方案规划完成后，主智能体直接调度对应子代理进入第二阶段受控写入，若判定为无需更新则跳过第二阶段直接进入第三阶段。
  - 全流程严禁在终端输出任何需要人工确认的话术，严禁挂起等待用户回复。

## 第二阶段：受控写入与专业子代理委派

方案规划完成后，主智能体按领域职责委派专项子代理，主智能体负责统筹与把关，各专项子代理各司其职，严禁跨领域串碰。

- 任务书一：跨仓契约与领域影响分析子代理：
  - 职责：深入各代码仓，提取跨仓契约与事实差异，产出客观推导报告。
  - 提示词模板：
    ```markdown
    请深入工作区兄弟仓（/srv/workspace/*），全面检索 Controller 路由、RPC 契约、MQ 主题生产消费实现与 Flyway/DDL 数据库变更。
    根据代码客观事实推导跨仓影响，执行三路自主决策树判定，并起草包含客观证据链的业务域演进方案记录。
    ```
- 任务书二：新领域初始化子代理：
  - 职责：开辟全新业务领域目录骨架，一次建齐全部六大分类目录与基础索引。
  - 提示词模板：
    ```markdown
    请针对新业务领域在系统知识库根目录下建立领域目录（/srv/workspace/system-knowledge/<新业务领域中文名>/）。
    按照统一规范，一次建齐全部六大分类单数目录（flow/、module/、rule/、interface/、data/、runbook/）。
    创建领域导航文件 index.md 与 overview.md，并在系统根目录 index.md 中登记新业务领域与代码仓归属映射，在 db-map.md 中补齐数据库映射。
    ```
- 任务书三：跨仓主流程子代理：
  - 职责：横向梳理兄弟仓交互行为，起草或更新跨仓主流程文档。
  - 提示词模板：
    ```markdown
    请深入兄弟代码仓源码事实，核查两端请求与消息交接、业务关联键（如订单号、批次号）流转、状态归属与失败补偿传播机制。
    在目标业务领域 flow/ 目录下编写或更新跨仓主流程文档（flow-<topic>.md），确保端到端主链路清晰完整，严禁机械拼接局部文档。
    ```
- 任务书四：接口与数据模型子代理：
  - 职责：核对跨服务契约交接，维护全局数据库映射与结构快照。
  - 提示词模板：
    ```markdown
    请核对本次变更涉及的对外 HTTP/RPC 接口与 MQ 消息契约，在目标业务领域 interface/ 目录下起草或更新契约文档。
    若涉及数据库结构变更，核对并更新系统知识库根目录 db-map.md 与 ddl/ 目录下的数据库快照（保留字段语义补丁节）。
    ```

## 第三阶段：零断链验收与推进检查点水位

子代理完成写入后，主智能体执行统一自检门禁、发布与检查点推进闭环：

- 断链自检自愈门禁（核心红线）：
  - 在系统知识库根目录运行断链校验：
    ```bash
    ad run workspace/links.verify --profile skm -- path="/srv/workspace/system-knowledge"
    ```
  - 校验系统根目录索引、各业务领域索引与六大分类文档之间的全部相对链接与标题锚点。
  - 若存在断链（`brokenCount > 0`），主智能体立即指派对应子代理或就地修复至零断链（`brokenCount === 0`）方可放行。
- 工作区状态审查：
  - 核查修改严格收敛于系统知识库内部：
    ```bash
    ad run workspace/bash.exec --profile skm -- command="git status" cwd="/srv/workspace/system-knowledge"
    ad run workspace/bash.exec --profile skm -- command="git diff" cwd="/srv/workspace/system-knowledge"
    ```
- 统一发布推送：
  - 系统知识文档统一提交并推送到 `master` 分支：
    ```bash
    ad run maintenance/maintenance.publish --profile skm -- path="/srv/workspace/system-knowledge" repoType="system_knowledge" message="docs(system): sync domain knowledge and cross-service flows"
    ```
- 推进检查点水位（绝对交付标志）：
  - 无论是否产生实质文档改动，最后必须调用检查点推进动作：
  - 有文档更新场景（publish 提交后会在 master 分支生成全新提交，必须将 publish 出参返回的 commit 哈希或当前 HEAD 传入 commit 参数）：
    ```bash
    ad run maintenance/maintenance.complete --profile skm -- path="/srv/workspace/system-knowledge" commit="<PUBLISHED_COMMIT_OR_HEAD>" actionTaken="docs_updated" summary="<系统知识更新说明>"
    ```
  - 无需更新文档场景（未产生新提交，沿用目标检查点）：
    ```bash
    ad run maintenance/maintenance.complete --profile skm -- path="/srv/workspace/system-knowledge" commit="<TO_COMMIT>" actionTaken="no_change_needed" summary="<系统级跨仓契约与全局领域未失效，无需更新>"
    ```
